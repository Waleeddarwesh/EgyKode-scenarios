# A password nobody types

Wait for setup, then write the configuration that generates a credential
instead of accepting one:

```
until curl -s --max-time 5 http://localhost:4566/_localstack/health 2>/dev/null | grep -q secretsmanager; do sleep 3; done
cd /root/iac
cat > main.tf <<'HCL'
provider "aws" {
  region                      = "us-east-1"
  access_key                  = "test"
  secret_key                  = "test"
  skip_credentials_validation = true
  skip_requesting_account_id  = true
  skip_metadata_api_check     = true
  endpoints {
    secretsmanager = "http://localhost:4566"
    sts            = "http://localhost:4566"
    iam            = "http://localhost:4566"
  }
}

resource "random_password" "db" {
  length           = 24
  special          = true
  override_special = "!#$%&*-_=+"
}

resource "aws_secretsmanager_secret" "db" {
  name                    = "platform/db/credentials"
  recovery_window_in_days = 0
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id = aws_secretsmanager_secret.db.id
  secret_string = jsonencode({
    username = "app"
    password = random_password.db.result
    host     = "127.0.0.1"
    port     = 5432
    dbname   = "shop"
  })
}
HCL
terraform apply -auto-approve -no-color | tail -4
```{{exec}}

**`recovery_window_in_days = 0`** because this is a lab. The default is 7, which
means a deleted secret is recoverable for a week — and that the *name* stays
reserved for that week, so recreating it with the same name fails with
`InvalidRequestException: You can't create this secret because a secret with
this name is already scheduled for deletion`. That error is the usual reason a
second `terraform apply` fails after a `destroy`.

## What is stored, and what is not

```
cd /root/iac
awslocal secretsmanager get-secret-value \
  --secret-id platform/db/credentials --query SecretString --output text | jq .
```{{exec}}

**The endpoint is in there with the password.** That is deliberate and it is
the difference between a secret an application can use and a secret it can only
half use: one fetch and it has everything it needs to connect. Nothing about
the database lives in the application's configuration, which is what makes step
3 possible.

## Now check the claim: is it in a file you wrote?

```
cd /root/iac
PW=$(awslocal secretsmanager get-secret-value --secret-id platform/db/credentials \
  --query SecretString --output text | jq -r .password)
# An empty needle would make grep match every line and report a leak that is
# not there, so check we actually read a password first.
[ -n "$PW" ] || { echo "could not read the password - is jq installed?"; }
echo "the password is ${#PW} characters"
echo "--- searching the configuration you wrote ---"
if [ -n "$PW" ] && grep -rn -F -- "$PW" *.tf; then
  echo "FOUND in a .tf file"
else
  echo "not in any .tf file"
fi
```{{exec}}

True: it appears in no configuration file. Nobody chose it, nobody typed it,
and it is not in version control.

## And now the part the criterion does not say out loud

```
cd /root/iac
PW=$(awslocal secretsmanager get-secret-value --secret-id platform/db/credentials \
  --query SecretString --output text | jq -r .password)
echo "grep for it in the state file:"
grep -c -F -- "$PW" terraform.tfstate
echo "ask jq for the attribute instead:"
jq -r '.resources[] | select(.type=="random_password") | .instances[0].attributes.result' terraform.tfstate
```{{exec}}

**`grep` found nothing. `jq` found the password.**

Look at why before drawing the wrong conclusion. State is JSON, and JSON escapes
some characters — a `&` in the password is stored as `\u0026`, so the literal
string you searched for is not the byte sequence in the file:

```
cd /root/iac
jq -r '.resources[] | select(.type=="aws_secretsmanager_secret_version") | .instances[0].attributes.secret_string' terraform.tfstate
```{{exec}}

So **"I grepped the file and the password was not there" is not evidence.** It
is one of the more comfortable ways to be wrong about a leak, and it applies to
any JSON you search this way — state files, log exports, API responses.

**The password is in `terraform.tfstate`, in plaintext.** Terraform stores every attribute
of every resource it manages, and `random_password.result` is an attribute. The
`sensitive` marking only stops it printing to your terminal; it changes nothing
about the file.

So "generated by Terraform and appears in no file you wrote" is exactly true and
slightly misleading. The rules that follow from it are the ones that matter:

- **State is a credential.** Treat the file the way you would treat the password.
- **Never commit it.** `.gitignore` `*.tfstate*` on the first commit, not after.
- **Remote state must be encrypted**, with access controlled — an S3 bucket with
  encryption and a policy, not a shared drive.
- **A generated password is still better than a typed one**, because it is
  strong, unique, rotatable and never in a chat message. State is one file you
  can protect; a password pasted into three places is not.

**Done when:** a 24-character password Terraform generated is in Secrets
Manager, and appears in none of your `.tf` files.
